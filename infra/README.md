# Инфраструктура

Всё живёт на одной машине в Azure: `vm-raw2reel`, Sweden Central,
`Standard_B4als_v2` — 4 vCPU и 8 GB RAM (до 04.11.2026 было 2 и 4). Там же крутится CI — Gitea с Actions, потому что GitHub-аккаунт
заблокирован и Actions на нём недоступны.

## Что где

Два отдельных compose-проекта, и это сделано намеренно.

`raw2reel` — инфраструктура, лежит на хосте в `/opt/raw2reel/infra` и в
репозитории не версионируется: Caddy, Gitea, act_runner.

`raw2reel-apps` — приложения, описаны здесь в `compose/docker-compose.apps.yml`
и разворачиваются из CI. Сеть `raw2reel_edge` создаётся инфраструктурным
проектом, приложения подключаются к ней как к внешней.

Разделение нужно, чтобы деплой приложения не мог уронить Gitea, которая этот
деплой выполняет. Конфиг Caddy разделён по той же причине и в три слоя:

- главный `Caddyfile` — только снипеты и внутренний healthcheck;
- `conf.d/05-apex.caddy` на хосте — блок апекса и маршрут Gitea, репозиторию
  и деплою недоступен;
- `apps.d/10-apps.caddy` — маршруты приложений из `caddy/apps.caddy` этого
  репозитория, импортируются **внутрь** блока апекса.

Поэтому `caddy/apps.caddy` не самостоятельный site-блок, а набор `handle`.
Если деплой положит туда негодный файл, Caddy отвергнет конфиг целиком и
останется на прежнем, а `deploy.sh` откатится — Gitea при этом не пострадает.

## Маршруты

Всё на одном имени, потому что A-запись есть только у апекса:

- `raw2reel.studio/` — фронтенд
- `raw2reel.studio/api/*` — бэкенд
- `raw2reel.studio/ml/*` — ML-сервис
- `raw2reel.studio/git/` — Gitea

Gitea под подпутём, а не на своём имени: отдельная A-запись тогда не нужна, и
сертификат апекса покрывает её сам. Префикс снимается `handle_path`, потому что
Gitea знает про подпуть из `ROOT_URL` и ждёт путь уже без него.

Публичный префикс `/ml/*`, а контейнер и каталог называются `ai`: снаружи
сервис представлен как ML, внутренние имена не переименовывались.

У бэкенда и ML три эндпоинта. `/health` отвечает, пока жив процесс, и не
трогает внешние сервисы — его опрашивает healthcheck контейнера. `/ready`
проверяет зависимости и используется деплоем перед переключением трафика.
`/version` отдаёт sha развёрнутого образа.

Сертификаты Let's Encrypt Caddy берёт сам. Для `api.*` и `git.*` нужны
A-записи на `20.240.128.170`.

## Рендер: две фазы и очередь

AI-сервис принимает не одну заявку, а две, и это его контракт, а не наше
усложнение. `POST /v2/prepare` по видео собирает каталог персонажей с
превью; `POST /v2/render` по этому каталогу и выбранным персонажам собирает
ролик. Прежней одношаговой ручки `/v1/render` больше нет.

Снаружи это выглядит так:

- `POST /api/analyses` с `sourceMediaId` — ставит разбор в очередь, отвечает
  `202` и идентификатором;
- `GET /api/analyses/{id}` — состояние и карточки персонажей, превью
  отдельными ссылками;
- `POST /api/renders` с `analysisId` и выбранными `personIds` — рендер. Если
  прислать только `sourceMediaId`, воркер разберёт видео сам и выберет
  персонажей по числу появлений, так что однокнопочный сценарий работает без
  выбора.

Между бэкендом и AI-сервисом — NATS с JetStream и один воркер. Воркер один
намеренно: в AI-сервисе общий замок на prepare и render, второй воркер лишь
спорил бы за тот же слот и получал `429`. Пока работа идёт, воркер раз в
минуту продлевает срок подтверждения (`working()`), иначе JetStream переотдал
бы сообщение посреди рендера.

Ответ prepare весит до 16 MB, поэтому сырые байты и превью лежат в Blob
(контейнер `analyses`, удаление через 7 дней), а в Cosmos — только компактные
карточки: документ там ограничен 2 MB. Исходник на рендер берётся из записи
разбора, а не из запроса: сервис сверяет каталог с SHA-256 видео и другой файл
отвергает.

Состояние очереди: `docker compose -f /opt/raw2reel/apps/docker-compose.apps.yml logs worker`
и `curl -s localhost:8222/jsz?streams=1` изнутри контейнера `nats`.

## Сэмплы

Готовые треки и видео — это обычные медиа, принадлежащие служебному владельцу
`samples`. Так их видит каждый, а правило «медиа принадлежит владельцу»
остаётся в силе: `GET /api/samples` показывает каталог,
`POST /api/samples/{id}` кладёт пользователю **копию**, и дальше он идёт
обычным путём через `/analyses` и `/renders`. Копия, а не ссылка, намеренно:
разбор и рендер проверяют владельца, и делать для сэмплов исключение из этой
проверки не стоит. Копирование идёт потоком, видео на сотню мегабайт в память
бэкенда не попадает.

Засев — `infra/scripts/seed-samples.sh`, через API так нельзя: он создаёт
записи только на владельца из сессии.

```
./infra/scripts/seed-samples.sh track1.mp3 track2.mp3
```

## Выход к Meta через вторую машину

Модели Meta не отдаются на адрес нашего хоста. Измерено 02-03.11.2026: с
`20.240.128.170` (Azure `swedencentral`) `POST /v1/responses` отвечает
`404 model_not_found` 40 раз из 40, а тем же ключом в ту же минуту с машины в
другом регионе — `200`. Ключ сверен побайтно, узел Meta подменялся через
`--resolve` в обе стороны, версия IP ни при чём. Каталог `GET /models` при
этом обманчив: он то пуст, то отдаёт девять моделей с обеих сторон, поэтому
«список получаю, значит работает» ничего не доказывает — проверять надо
только сам вывод.

Поэтому запросы AI-сервиса к `api.meta.ai` уходят через прокси на отдельной
маленькой машине в `indiasouthcentral`. Всё остальное остаётся здесь: видео
никуда не едет, через океан идут только вызовы API.

```
Швеция                                  Индия (1 ГБ, входящих портов нет)
ai ──HTTPS_PROXY──> 172.18.0.1:8888 <── ssh -R ── tinyproxy ──> api.meta.ai
```

Туннель поднимает индийская сторона, поэтому там не открыто ни одного
входящего порта. На шведской стороне ключ записан в `~/.ssh/authorized_keys` с
`restrict,port-forwarding`: оболочки у него нет, только проброс.

Настройка машины — `infra/india/setup.sh`, он идемпотентен. Единственное, что
нельзя сделать оттуда, — разрешить привязку не к петле; это root на шведской
стороне:

```
echo 'GatewayPorts clientspecified' | sudo tee /etc/ssh/sshd_config.d/60-raw2reel-tunnel.conf
sudo systemctl restart ssh
```

Без этой строки sshd **не ругается**, а молча вешает порт на `127.0.0.1`, и
контейнеры его не видят. Проверять глазами: `ss -ltn | grep 172.18.0.1:8888`.

**Ловушка `NO_PROXY`.** Сравнение идёт по окончанию имени хоста, поэтому
запись `ai` (имя контейнера) исключает из проксирования `api.meta.ai`. Выглядит
это обманчиво: внешний адрес показывает Индию, а Meta отвечает 404, потому что
запросы к ней идут напрямую. В `NO_PROXY` держим только петлю; `deploy.sh`
проверяет это отдельно.

Если рендер снова начал падать на моделях, порядок такой: `deploy.sh` при
выкладке проверяет внешний адрес контейнера `ai` и валит развёртывание, если
прокси не отвечает. Вручную — `systemctl status meta-tunnel` на индийской
машине и та же проверка `ss` здесь.

## Откуда приходят изменения

Источник истины — **GitHub**, `drakeaifoce/raw2reel`. Туда пушат, оттуда
изменения попадают в Gitea, и уже пуш в Gitea запускает конвейер.

Переносит их опрашиватель на машине: systemd-таймер `github-sync.timer`
каждые две минуты сравнивает sha ветки `main` на GitHub и в Gitea и при
расхождении переносит. Именно переносит обычным `git push`, а не
зеркалированием — на это есть две причины. Webhook на GitHub добавить нельзя,
у нас нет admin на репозитории. А синхронизация зеркала Gitea не порождает
события `push`, на котором висят Actions, то есть конвейер от неё просто не
запустится.

Скрипт лежит вне репозитория, в `/opt/raw2reel/bin/github-sync.sh`, и это
намеренно: то, что запускает развёртывание, не должно подменяться самим
развёртыванием — иначе один сломанный коммит обрывает связь, и починить её
можно только руками. По той же причине вне репозитория живут маршрут Gitea и
`runner.yaml`.

Что полезно знать:

```bash
systemctl list-timers github-sync      # когда следующий запуск
journalctl -u github-sync -n 20        # решение каждого запуска
sudo systemctl start github-sync       # перенести прямо сейчас, не дожидаясь
sudo systemctl stop github-sync.timer  # приостановить доставку
```

Опрашивателю нужен classic PAT со scope `repo` в
`/opt/raw2reel/secrets/github-token`. Fine-grained токен не подойдёт: такие
нацеливаются только на репозитории своего владельца, а `raw2reel` принадлежит
другому пользователю. Без файла с токеном скрипт не падает, а пишет в журнал,
что простаивает.

### Чего эта схема не умеет

**Проверки на pull request'ах GitHub не запускаются.** Следим только за
`main`, а `ci.yml` висит на push в main и на `pull_request` внутри Gitea — до
PR, открытого на GitHub, он не доходит. Закрыть разрыв можно только через
GitHub Actions, то есть получив admin у владельца репозитория.

Задержка — до двух минут, интервал опроса. Мгновенного запуска у этой схемы
не бывает по определению.

## Конвейер

`ci.yml` на пуш и pull request: определяет затронутые проекты и гоняет для них
линтеры, типы, тесты и сборку. `deploy.yml` на пуш в `main`: собирает образы
изменившихся проектов, помечает их sha коммита и вызывает `scripts/deploy.sh`.

Реестра нет. Хост один, образы собираются прямо в его docker-демон через
смонтированный сокет — это убирает push/pull и экономит место на диске
в 30 GB без temp-диска. Цена: истории образов вне хоста не остаётся.

Затронутые проекты считает `scripts/changed.sh` обычным `git diff`, без
сторонних actions. Правка `infra/` или `.gitea/` считается касающейся всех
трёх приложений: меняется способ сборки.

## Версия образа

`deploy.yml` передаёт каждой сборке `--build-arg GIT_SHA=<sha>`, Dockerfile
превращает его в переменную окружения, а `/version` её отдаёт. Версия
вплавлена в слой образа и поэтому не может разойтись с тем, что развёрнуто —
файла с версией в репозитории нет намеренно, его забывали бы обновлять.

`ARG` и `ENV` стоят в Dockerfile как можно позже: значение меняется каждую
сборку, и слои с зависимостями выше должны оставаться в кэше.

Проверить, что деплой доехал: `curl https://raw2reel.studio/api/version`.
Шаг проверки в `deploy.yml` сверяет версию только у тех сервисов, что
пересобирались, — остальные остаются на прежних тегах, и это нормально.

## Откат

`deploy.sh` перед переключением сохраняет текущие теги в `.env.prev`. Дальше
ждёт `healthy` от каждого контейнера, затем отдельно спрашивает `/ready` у
бэкенда и AI-сервиса — healthcheck говорит только о живости процесса, а
готовность зависимостей это другой вопрос. На любом провале возвращает
прежние теги и перезагружает Caddy.

Ненастроенная зависимость неготовностью не считается: пока Cosmos не создан,
деплой не должен из-за него откатываться.

## Деплой руками

Если CI недоступен, `scripts/deploy.sh` запускается с хоста напрямую — но
**из копии репозитория, совпадающей с развёрнутым коммитом**. Скрипт берёт
`caddy/apps.caddy` и compose-файл из своего рабочего дерева, поэтому
устаревшая копия поставит устаревшие маршруты. На практике это ловится
сразу: Caddy отвергает конфиг (например `ambiguous site definition`, если в
копии ещё лежит старый вариант `apps.caddy` с полным site-блоком), деплой
откатывается, сайт остаётся жив. Но время тратится.

На машине для этого есть `~/work/raw2reel` с remote `gitea`. Перед запуском:

```bash
cd ~/work/raw2reel && git fetch gitea main && git checkout -B main FETCH_HEAD
```

Каталоги `apps/`, `apps.d/` и `conf.d/` принадлежат обычному пользователю:
задача CI работает в контейнере от root и пишет в них всё равно, а владение
пользователем нужно, чтобы деплой руками не упирался в права.

## Секреты

Боевые значения — в секретах Gitea Actions. Деплой рендерит из них
`/opt/raw2reel/secrets/app.env` с правами 600, compose подключает его через
`env_file`. Состав ключей описан в корневом `.env.example`, значений там нет.

В Azure сейчас используются ключи доступа. Правильнее была бы managed identity
у машины — тогда секретов в окружении не нужно вовсе, — но назначение
RBAC-ролей требует прав, которых у роли Contributor нет.

## Токены регистрации runner

Постоянного токена регистрации не хранится намеренно: он позволяет
зарегистрировать чужой runner, а тот получает docker-сокет хоста, то есть
фактически root. Токен выпускается на одну операцию и отзывается после.

Выпустить:

```bash
curl -X POST -H "Authorization: token $(cat /opt/raw2reel/secrets/gitea-token)" \
  http://127.0.0.1:3000/api/v1/repos/nik/raw2reel/actions/runners/registration-token
```

Отозвать все выпущенные — `UPDATE action_runner_token SET is_active=0` в
`/srv/gitea/gitea/gitea.db`; это то же, что кнопка reset в интерфейсе. Уже
зарегистрированный runner не пострадает, его учётные данные лежат отдельно, в
`/srv/runner/.runner`.

## Ограничения, про которые надо знать

Задаче CI смонтирован docker-сокет, то есть фактически права root на хосте.
Допустимо, пока Gitea однопользовательская и регистрация в ней закрыта.

`runner.yaml` ограничивает задачу 1500 MB и держит `capacity: 1`:
параллельная сборка конкурирует за процессор с рендером, а он занимает всё,
что дают. Метки указывают на
`node:24`, а не 20: `frontend/package.json` требует `engines.node >=22.12`.

GPU недоступен: у всех GPU-семейств квота 0/0 и повысить её на этой подписке
нельзя. Любая обработка идёт на CPU.

## Доступ к Gitea

`https://raw2reel.studio/git/` — веб-интерфейс, он же адрес для git по HTTPS:

```
git clone https://raw2reel.studio/git/nik/raw2reel.git
```

`ROOT_URL` равен `https://raw2reel.studio/git/`, и этот же адрес задачи
получают как `github.server_url`, поэтому `actions/checkout` работает штатно.
На Azure это не очевидно: трафик из контейнеров на собственный публичный IP
должен развернуться обратно — проверено, разворачивается.

Gitea дополнительно опубликована на `127.0.0.1:3000` (только петля, наружу
порт закрыт) — удобно для вызовов API с хоста без токена в URL; этим
пользуется `ciwatch.sh`. Обязательной эта публикация больше не является.
